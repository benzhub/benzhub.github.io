Backoff 退避策略是什麼？Exponential Backoff 指數退避完整教學

2024/01/08 2026/11/11
javascript networking

API 暫時失敗時，退避策略會讓下一次嘗試晚一點發生；指數退避把等待上限逐次加倍，jitter 再把同時失敗的客戶端錯開。它適合可安全重試的暫時性錯誤，不會修好錯誤參數、權限問題或永久故障。

先判斷這個請求能不能重試

讀取資料的 GET 通常適合重試。付款、建立訂單等寫入操作可能已在伺服器成功，只是回應遺失；沒有冪等鍵或服務端去重機制時，直接重送可能造成重複交易。即使遇到 500，也先確認 API 契約。常見候選是 429、502、503、504 和暫時的網路錯誤；400、401、403、404 通常要先修請求或權限。Retry-After 若存在，應優先尊重伺服器的等待要求。參考 AWS 的重試與冪等說明。

指數退避與 Full Jitter 怎麼算

若第一個重試的編號為 0，可先算 cap = min(maxDelay, baseDelay × 2^retryIndex)，再從 0 到 cap 隨機取值。假設 baseDelay=1000 ms、maxDelay=8000 ms，各次重試上限為 1000、2000、4000、8000 毫秒。實際等待值不是固定的 1、2、4、8 秒，可能小於上限。Full Jitter 的目的在分散大量客戶端的重試時間；參考 AWS SDK 重試公式。

可執行的 JavaScript 範例

把以下程式存成 retry.mjs，用 Node.js 執行。這裡注入假回應，示範 503 → 429 → 200，不會對外發 HTTP 請求。正式使用時把 fetchImpl 改成預設的 fetch，並傳入真實 URL。

const sleep = ms => new Promise(resolve => setTimeout(resolve, ms));

function retryAfterMs(value, now = Date.now()) {
  if (!value) return 0;
  if (/^\d+$/.test(value.trim())) return Number(value) * 1000;
  const date = Date.parse(value);
  return Number.isNaN(date) ? 0 : Math.max(0, date - now);
}

async function fetchWithRetry(url, {
  fetchImpl = fetch, wait = sleep, attempts = 3,
  baseDelay = 1000, maxDelay = 8000, random = Math.random,
} = {}) {
  if (!Number.isInteger(attempts) || attempts < 1) {
    throw new RangeError('attempts 必須至少為 1');
  }
  for (let attempt = 0; attempt < attempts; attempt++) {
    let response;
    try {
      response = await fetchImpl(url);
    } catch (error) {
      if (attempt === attempts - 1) throw error;
    }
    if (response?.ok) return response;
    if (response && ![429, 502, 503, 504].includes(response.status)) {
      throw new Error(`不重試 HTTP ${response.status}`);
    }
    if (attempt === attempts - 1) {
      throw new Error(`重試次數已滿；最後狀態：${response?.status ?? '網路錯誤'}`);
    }
    const cap = Math.min(maxDelay, baseDelay * 2 ** attempt);
    const jitter = Math.floor(random() * cap);
    const serverWait = retryAfterMs(response?.headers.get('Retry-After'));
    await wait(Math.max(jitter, serverWait));
  }
}

const statuses = [503, 429, 200];
const fakeFetch = async () => {
  const status = statuses.shift();
  console.log(`HTTP ${status}`);
  return new Response('OK', {status});
};
const result = await fetchWithRetry('https://example.invalid/api', {
  fetchImpl: fakeFetch,
  wait: async ms => console.log(`等待 ${ms} ms（示範省略實際等待）`),
  random: () => 0.5,
});
console.log(await result.text());

執行 node retry.mjs，預期會看到 HTTP 503、等待 500 ms、HTTP 429、等待 1000 ms、HTTP 200、OK。attempts=3 指總請求次數，不是「原請求之外再試三次」。正式 API 需要額外考慮總逾時、取消、紀錄及多層 SDK 重試疊加；不要讓前端、後端與 SDK 各自無限制重試。

如果 429 回應包含 Retry-After: 5，程式至少會等五秒；該標頭也可能是 HTTP 日期。範例未設定總時間上限，因此伺服器要求很長的等待時，使用者可能一直等不到結果。互動操作應自行設截止時間，或回傳「稍後重試」給使用者。範例的假回應沒有標頭，所以才可快速看到 500、1000 毫秒的確定輸出。

什麼時候不該用同一套重試策略

背景任務容許較長等待，互動操作可能只容許幾秒。Retry-After 是服務端提示，可能讓等待超出前端可接受的總時間；需要設總截止時間並通知使用者。輪詢中的「下次正常查詢」和「失敗後退避」也應分開，避免請求重疊；實作輪詢請看 前端 Polling 教學。
