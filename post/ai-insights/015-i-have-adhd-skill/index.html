AI 回答像論文？i-have-adhd 讓 coding agent 先講下一步 | AI Insights

2026/10/27
ai-insights AI AI coding Claude Code Codex Skill 開發效率

AI 講了 800 字，我只想知道下一步。 你貼上測試錯誤，它先稱讚你問得好，再介紹認證系統的歷史，最後說「建議檢查相關設定」。謝謝，我的測試還是紅的。i-have-adhd 就是為這種時刻設計的 Skill：讓 coding agent 先把「現在做什麼」講清楚，再補上必要細節。

這是什麼？AI 的「先講重點」開關

i-have-adhd 是 Ayoub Ghriss 製作的 AI coding agent Skill。它的核心是一份 SKILL.md，用規則指定 AI 怎麼呈現答案。

它不會幫模型升級大腦，也不會神奇地讀懂你的整個專案。比較像把 AI 那位「每次報告都要從創世紀講起」的同事拉到白板前，請他先寫：第一步是什麼？

名字裡有 ADHD，但作者的 README 說得很明白：不需要 ADHD 診斷也能使用。 這裡的笑點是 AI 太會繞路，不是拿 ADHD 本身開玩笑。

它到底改了什麼？先看一個場景

你問：「登入測試回傳 401，接下來查哪裡？」

一般模式：「這是一個很好的問題。401 可能涉及 token、cookie、session、中介層、環境變數……」你看到第三段，已經打開另一個分頁查午餐了。

啟用後，理想的回答會像這樣：

先確認失敗的請求有沒有帶 Authorization header。

  1. 打開失敗的測試，找到送出請求的程式碼。
  2. 對照成功測試的 header 設定。
  3. 重跑這支測試，記下第一個失敗訊息。

下一步：貼出失敗請求的 header 片段。

這是示意回答，不是說 401 一定由 header 造成。好的精簡回答，應該把要驗證的假設講清楚，而不是用很有自信的語氣亂猜。

10 條規則，濃縮成 4 件事

官方 Skill 列了 10 條規則。實際讀起來，它主要在做這四件事：

  1. 第一句就給行動。 有指令、路徑或答案，就先放前面。省掉「Great question!」的暖場，畢竟 bug 不會因為被稱讚就自己消失。
  2. 多步驟工作用編號。 一步只做一件事，清單最多五項。與其端出 27 點「完整指南」，不如先讓人真的做完前三步。
  3. 每輪交代進度。 長任務要說「第 3/5 步完成，下一步是……」；做完也要說什麼已經能用了。隔天回來，不必像考古一樣翻對話紀錄。
  4. 結尾只留一個下一步。 不要最後突然加碼「順帶一提，你的依賴套件、命名規則與人生規劃也值得改善」。

它還要求具體時間估計、平實報錯，並壓住無關的岔題。重點是：規則整理的是輸出，不應限制分析。 需要理解原理時，可以直接要求詳細解釋；碰到刪除資料、強制推送或 schema migration，安全確認也不能被「簡短」兩個字吃掉。

怎麼安裝？先手動開，不用一上來就簽終身契約

依照作者的 安裝文件，Claude Code 可以這樣裝：

claude plugin marketplace add ayghri/i-have-adhd
claude plugin install i-have-adhd@i-have-adhd

接著在對話中輸入 /i-have-adhd。Codex 的安裝方式是：

codex plugin marketplace add ayghri/i-have-adhd --ref main
codex plugin add i-have-adhd@i-have-adhd

在 Codex 對話中輸入 $i-have-adhd 啟用。安裝後預設不會自動開啟；你要明確呼叫，規則才會在那次對話中生效。想切回一般回答，可以說 stop adhd mode 或 normal mode。

我的建議是先挑一個真實卡住的任務試。若你只是想問「這個錯誤先查哪裡」，它很合適；若你在學 OAuth 原理，直接請 AI 詳細講解，別讓「簡潔」把課本撕成便條紙。安裝指令可能隨版本變動，動手前以官方文件為準。

作者的評測：有進步，也有一個很值得看的翻車案例

作者的 評測報告 使用 14 個案例，每種條件跑 3 次。加權平均從 4.05 升到 4.47；「可執行性」從 3.91 升到 4.62，「簡潔度」從 3.43 升到 4.57。14 個案例中，啟用後贏 10、平 2、輸 2。

看起來很漂亮，但先別急著把它封為「AI 廢話終結者」。這是作者自己的評測，評審模型與生成回答的模型屬於同一家族，每個案例也只有三次試驗。更何況作者設定的 release gate 沒有通過：啟用後仍有 3 個阻斷問題。

其中一個退步案例很有警示性：AI 把「可能缺少認證 header」說成了已經確定的原因。這正是我最在意的風險——答得短又篤定，錯的時候反而更難察覺。 遇到明確的「原因是……」，仍要看 log、測試和程式碼是否真的支持這個結論。

我會在哪些時候用？

趕著 Debug、跨檔案重構、或等 agent 交接進度時，我會想要這種回答格式：先講下一步、標出進度、給我驗證方法。它省掉的是「從一大段話裡挖出待辦事項」的時間。

需要學概念、設計架構或處理高風險操作時，我會要求它把推理和不確定性展開。i-have-adhd 只是一個輸出模式，沒有替代技術判斷。這篇也沒有把作者的數據冒充成我在中文對話中的親自實測。

所以別急著問「它能不能讓 AI 變聰明？」更實際的問題是：AI 回完這句，你能不能在兩分鐘內開始第一步？ 如果可以，這個小小的 Skill 就已經替你省下一輪「所以我現在到底要幹嘛？」了。
